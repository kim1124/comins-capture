# Comins Capture 리서치 및 설계 검토 지침

> 2026-10-04 최신 실행 결정: SnapDOM 3.2.0 조건부 채택을 사용자 승인으로 확정했다. 초기 프로젝트 구조·README·개발 Playground·사이트 가이드 작성을 진행했다. 아래의 과거 채택 전 착수 제한은 이 승인으로 대체하며, G1~G4 미완료는 릴리즈 조건으로 유지한다. 현재 구현과 잔여 항목은 [개발 가이드](guide/README.md)와 [실행 기록](worklogs/2026-10-04-initial-project.md)을 따른다.

이 문서는 [1차 리서치 초안](research.md)을 후속 조사와 설계 검토에서 사용하는 방법을 정한다. 제품 구현 명세나 구현 승인 문서는 아니다. 작성 기준일은 2026-10-02이다.

후속 실행 근거는 [캡처 엔진 1차 실증 비교](capture-engine-comparison.md)에 기록한다. 해당 실증에서 발견한 live 폼 상태, 내부 스크롤·sticky, 소수 픽셀 반올림, 엔진별 width 옵션 의미 차이를 후속 검토에서 유지한다. SnapDOM 우선 검증은 권고이며 채택 확정이 아니다.

[SnapDOM 보완 검증](snapdom-followup.md)에서 단일 sticky 복제본 보정 가능성과 경고 없는 폰트 누락을 확인했다. 해당 보정을 일반적인 sticky 지원으로 확대 해석하지 않고, 자원 준비·취득·결과 삽입 검증을 엔진 경고와 별개로 검토한다.

[실제 브라우저 공통 검증 화면](browser-workbench.md)에 Chrome·Safari 직접 조작과 실행별 증거 저장 결과를 기록한다. Safari의 폼 외형 차이·sticky 누락·폰트 재요청 실패를 후보 엔진 평가에 반영하며, 단일 fixture 실행을 브라우저 전체 지원 완료로 확대 해석하지 않는다.

[SnapDOM 보완 구현 검토](snapdom-repair-review.md)에 중첩 sticky·부모 끝 경계 보정, 폰트별 누락 검사와 출력 중단 결과를 기록한다. 기본 폼 외형 보존은 미해결이며 CSS 지정 폼의 성공으로 대체하지 않는다. 폰트 삽입 개수만으로 자원 완전성을 판정하지 않고 필요한 자원별 증거를 확인한다. 연구용 고정 ID·엔진 내부 스타일 자료에 의존한 보정을 제품용 일반 어댑터로 취급하지 않는다.

초기 API·지원 범위의 구체화는 [명세 검토안](api-spec.md)을 참조한다. 기존 사용자 확정 결정과 새 API·기본값 제안을 구분하며, 검토안 작성 자체를 엔진 채택·제품 구현 승인으로 해석하지 않는다.

명세 검토 이후의 작업 순서는 [구현 준비 상태와 추가 검증](implementation-readiness.md) 및 [Core 구현 계획](superpowers/plans/2026-10-02-capture-core.md)을 따른다. 엔진 채택 전 G1~G4, 구현 중 회귀 검증, 실제 지원·출시 전 검증을 구분한다. 계획의 미실행 명령을 현재 저장소의 지원 명령이나 통과 결과로 보고하지 않는다.

## 2026-10-04 승인된 추진 순서

[단계별 엔진 전환 계획](superpowers/plans/2026-10-04-engine-transition.md)에 따라 외부 엔진 기반 초기 제품을 먼저 완성하고, 회귀 자료를 축적한 뒤 검증된 자체 엔진으로 교체한다. 자체 엔진 선행 개발 권고는 이 결정으로 대체한다. 공개 API와 자원·좌표·출력·오류·수명주기 계약은 Comins가 소유하며 엔진별 처리는 내부 adapter에 한정한다.

사용자 재확인: **범용 엔진 기반 기능 완성·첫 릴리즈가 1순위이며 자체 엔진으로 교체 가능한 구조는 필수**다. 초기에는 엔진 독립 타입·adapter·공통 계약 테스트와 릴리즈에 필요한 최소 보완을 구현한다. 미래 교체를 위한 범용 DOM/스타일 엔진 구현은 첫 릴리즈의 선행 조건으로 추가하지 않는다. 현 후보의 보완이 자체 엔진 수준으로 커지면 대안 범용 엔진을 먼저 검토한다.

현재 실행 우선순위는 외부 엔진의 G1 자원 통제 → G2 DOM 대응 → G3 SVG·자원 검증 → G4 Safari 타일 검증이다. G1~G4 통과 전 엔진 의존 제품 통합을 진행하지 않는다. 공개 확장으로 해결할 수 없어 핵심 경로 재작성이나 fork가 필요하면 범위를 확대하기 전에 전환 시점을 재판단한다. 자체 엔진 상세 구현과 공개 배포는 현재 계획 반영 작업에 포함하지 않는다.

G1의 다음 단위는 [자원 준비 계층 P0](superpowers/plans/2026-10-04-resource-preparation.md)다. 원본 관찰·자원 해결을 준비 DOM 생성보다 먼저 수행하며, 실제 원본의 외형·기하·상태를 보존할 수 있는지 제한적으로 확인한다. 추정 공수는 실측 후 갱신하고 범용 준비 계층이나 자체 엔진을 즉시 구현하는 것으로 확대하지 않는다.

## 정책 원본

공통 실행 정책은 [Comins Contract](https://github.com/kim1124/comins-governance/blob/main/COMINS_CONTRACT.md)가 소유한다. 이번 조사에서 확인한 버전은 v1.8이다. 로컬에서는 [상위 Governance 원본](../../governance/COMINS_CONTRACT.md)을 확인한다. 공통 정책·라이선스·민감정보·릴리스 규칙을 이 문서에 복제하거나 완화하지 않는다.

프로젝트의 Git·패키지 기준선이 생기면 실제 독립 저장소 루트를 확인하고 공식 `comins-reference` 절차로 공통 지침을 도입한다. 이 연구 문서를 정식 `AGENTS.md`·프로젝트 설정의 초기화 완료 증거로 취급하지 않는다.

## 유지할 확정 조건

- 브라우저 내부 실행을 우선하는 `comins-capture` npm 모듈이다.
- DOM의 화면·스타일 보존, 다중 출력, 사용자 지정 크기·용지 규격·영역 자르기를 목표로 한다.
- Vanilla·React·Vue·Svelte를 지원 대상으로 한다.
- SVG의 `foreignObject` 사용은 허용된다.
- 초기에는 기본 엔진 하나로 제공한다. 보완 효과가 검증된 경우에만 소비자 선택 기능을 추가하며, 초기 다중 엔진 자동 선택·전환은 포함하지 않는다.
- 초기 출시는 정지 캡처·크기·용지 규격·영역 자르기에 집중하고 PDF·녹화는 후속 단계로 둔다.
- 감지된 리소스 누락·요청 크기 또는 형식 불충족은 기본 오류로 종료한다. 소비자가 명시적으로 허용한 경우만 부분 결과·축소·형식 대체를 제공한다. 감지하지 못한 시각적 차이까지 보증하지 않는다.
- 초기 지원 목표는 데스크톱 Chrome·Edge·Firefox·Safari와 Android Chrome·iOS Safari이다. 기준일 2026-10-02의 일반 배포 최신 안정 버전을 기준으로 하며, 최신·직전 메이저 동시 지원이나 구버전 전체 호환성은 약속하지 않는다. WebView는 후속으로 둔다.
- 공식 기준 버전과 실제 검증 환경은 리서치의 버전 기록에서 구분한다. 기존 Chromium 151·Firefox 153·WebKit 26.5 실증을 최신 정식 브라우저의 지원 완료 근거로 사용하지 않는다. 이후 기준을 갱신할 때 조회일·공식 출처·검증 결과를 함께 남긴다.
- 용지 규격은 ISO·JIS를 명시적으로 제공하고, 체계를 생략하면 ISO를 적용한다.
- 기본 출력 해상도는 일반 DOM 이미지·Canvas의 경우 CSS 크기 기준 1배, 용지 규격의 래스터 출력은 300 PPI이다. 배율·출력 픽셀·PPI는 소비자가 조정할 수 있게 한다. 장치 DPR 적용은 명시적 선택이며 용지 PPI에 중복 곱하지 않는다.
- SVG는 크기·viewBox를 기준으로 하고 래스터 변환 시 출력 해상도를 적용한다. 출력 픽셀 수와 DPI 메타데이터를 구분하며 출력 한도 초과 시 기본 오류 정책을 유지한다.
- 초기에는 영역 자르기·고정 크기 분할을 제공한다. 문단·표 행 보존 분할은 후속 단계로 둔다.

2026-10-02 사용자 확정 근거와 영향은 [리서치의 결정 기록](research.md)에 남긴다. 특정 엔진 채택과 구현 착수는 별도이며 SnapDOM은 후속 검증 대상이다.

이미 답변받은 실행 환경·SVG 요구·엔진 제공 방식·초기 출시 범위·실패 처리 기본값·지원 브라우저 목표와 최신 버전 기준·용지 체계·분할 수준·기본 해상도와 사용자 조정 요구를 반복 확인하지 않는다. 새로운 증거가 기존 결정에 실질적인 영향을 줄 때만 변경 필요성을 설명한다.

## 증거와 결정 관리

1. 공식 문서의 주장, 고정 배포본의 정적 분석, 직접 실행 결과, 설계 권고를 구분한다.
2. 버전·조회일·출처·패키지 내부 파일 또는 공개 API를 함께 기록한다. 일시적인 로컬 경로를 영구 근거로 사용하지 않는다.
3. npm `latest`·라이브 문서·GitHub 기본 브랜치의 기능을 같은 버전의 사실로 혼합하지 않는다.
4. 공식 이슈가 열려 있다는 이유만으로 현재 제품 결함으로 확정하지 않는다. 닫힌 이슈는 회귀 시나리오로 활용한다.
5. 권고를 승인된 요구사항으로 승격하지 않는다. 변경된 결정은 해당 항목에 결정일·근거·영향을 기록한다.
6. 현재 초안은 미결정 사항이 있는 중간 산출물이다. 최종 명세로 전환하기 전에 범위에 영향을 주는 결정을 정리한다.

## 설계 검토 기준

- 특정 엔진의 공개 옵션을 Comins API로 그대로 노출하기 전에 의미와 기본값을 검토한다.
- 캡처 대상·crop 좌표·레이아웃 크기·출력 픽셀·DPR·PPI·용지 규격을 구분한다.
- 출력 형식과 반환 타입, 요청 MIME과 실제 MIME을 구분한다.
- 한 번의 화면 상태를 재사용하는 이미지 출력과 매 프레임 새 상태를 읽는 녹화를 구분한다.
- 이미지 생성 성공, 감지 가능한 리소스 누락 없음, 시각적 일치 검증을 별개의 결과로 다룬다.
- 원본 DOM·포커스·스크롤 보존과 취소·실패 시 정리 책임을 검토한다.
- 외부 리소스 재요청·프록시·업로드를 포함해 Contract의 네트워크 opt-in 경계를 확인한다.
- 마스킹은 시각적 덮개와 데이터 제거를 구분한다. 녹화 방식에 따라 구현 경로가 다름을 명시한다.
- 캡처 Core·프레임워크 연동·PDF·녹화의 책임을 구분하되, 패키지 분리는 아직 확정하지 않는다.
- 기존 모듈의 유용한 계약을 참고하되 코드를 복사·번들링·배포할 때의 라이선스 검토는 별도로 수행한다.

## 검증과 보고

실증 검증은 고정 버전·공통 fixture·명시한 브라우저 환경에서 수행한다. 첫 실행과 캐시 실행, 자동화 WebKit과 실제 Safari, 이미지 출력과 영상 녹화의 결과를 분리한다. 성능 수치에는 입력 크기와 측정 환경을 함께 기록한다.

조사만 수행했으면 구현·테스트 통과로 보고하지 않는다. 문서 변경에는 링크·내용 일관성·민감정보·서식 확인을 적용하고, 존재하지 않는 패키지 명령이나 전체 게이트를 만들어내지 않는다. 구현이 요청되면 실제 스택과 지원 명령을 확인하여 영향에 맞는 검증을 선정한다.

공개 문서에는 개인 연락처·로컬 사용자 경로·자격증명·불필요한 개인정보를 기록하지 않는다. 사례는 합성 데이터와 공개 프로젝트 주소를 사용한다. 공통 정책에서 요구하는 정식 스캔을 단순 텍스트 확인으로 대체했다고 보고하지 않는다.
